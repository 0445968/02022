## Exact implementation
- Staged `supabase/migrations/20261123235430_ct02e_story_revision_rls.sql` (filename generated by Supabase CLI v3.2.0 in isolated GitHub Actions run **45292742893**). **Not applied** to Supabase.
- `newsroom_private` schema is not exposed by the current REST Data API. Creates `newsroom_private.scope_matches` and `newsroom_private.has_staff_permission` as **SECURITY INVOKER**, explicitly scoped to current `auth.uid()`, active/unexpired memberships, active/unexpired role assignments, story assignments and capability grants. Explicit applicable DENY overrides win; `settings.security_admin` and `reader.personal` never come from staff grants. The function can read only the RLS-scoped staff tables authorized for the caller. No user metadata/legacy editor flags are used.
- Drops the six verified named legacy `stories` direct RLS policies for staff; installs scoped SELECT/INSERT/UPDATE/DELETE policies. **Preserves** the published-story public SELECT policy `stories_select_public` and its date/status filtering.
- Drops the four verified legacy `story_revisions` policies (which previously depended on `profiles.is_author/is_editor`) and installs scoped authenticated SELECT/INSERT/UPDATE/DELETE policies. A freelancer may create and update a revision for an assigned story but does NOT inherit revision deletion/publishing rights by being an author.
- Adds row triggers for direct authenticated `stories` UPDATE and `story_revisions` INSERT/UPDATE to defend against assignment changes, direct publication, scheduling, status escalation, slug/access tier and other protected metadata edits. These triggers are **not** a substitute for guarding privileged service-role writes or the existing SECURITY DEFINER publication function.
- No profile/editorial-profile/byline/stories/media records or existing story contents are modified. The draft migration changes policies and functions only, not data.

An isolated test does not constitute production authorization.

The following *direct-authorization escape hatches* are still open and must be secured in CT-02f and later:
1. **`public.publish_story_revision(p_story_id,p_user_id)`** remains authenticated-executable SECURITY DEFINER and checks `profiles.is_editor`. A revoked legacy editor could still invoke this directly even when the new server guard denies it. This must be rewritten with DB-resolved current capability and publishing tests before any rollout; do not revoke EXECUTE abruptly or break the working published revision flow.
2. **`public.story_versions`** still has legacy editor/author RLS and client-side direct historical version creation. Migrate without breaking version history and the atomic publishing workflow.
3. **`public.media_assets`** remains public SELECT with an `internal_notes` field, and old author/editor-based INSERT/UPDATE/DELETE. Review disclosure of internal metadata and the 21 approved/1 trashed status distribution, then design a public-safe rendering interface and scoped staff read/write.
4. **`storage.objects` media bucket** still grants mutations based on old author/editor flags. Public bucket settings can bypass download RLS and may expose files already linked by URL, so design storage behavior with published media compatibility; align upload/upsert/select/update/delete policies and ownership.
5. Other API routes, server actions and backend services may still authorize via `profiles.is_editor/is_author`. Complete inventory and convert together with RLS, RPC and storage; never treat a feature-flagged route alone as enforcement.
6. Owner identity, role presets, initial grants and membership backfill are unapproved and absent.
