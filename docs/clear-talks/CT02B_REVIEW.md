## Migration behavior and guardrails
Creates seven tables: `staff_memberships`, `staff_role_presets`, `staff_role_capabilities`, `staff_member_roles`, `staff_capability_overrides`, `staff_story_assignments`, `staff_access_audit` and a finite enum of capability names. All seven are RLS-enabled. Member, active-role, visible-capability, override, and assignment rows are SELECT-only for their authenticated owner; no user INSERT/UPDATE/DELETE policies. No anonymous privileges. The audit table has no user access and permits only SELECT/INSERT to service_role. Service-role bypasses RLS, so any future privileged mutation endpoint MUST verify current server capabilities and write an audit event in the same DB transaction; do not use service-role for read operations from client code.

Role preset **names** are seeded but role capability grants and membership rows are deliberately empty. This prevents automatic elevation of restored `is_editor` or `is_author` users. Existing story author/editor FK, published data, media, Auth, RLS and publishing RPC remain untouched.

**Important future work:** Active staff identity must be manually validated and backfilled via reviewed migration. Define approved preset capability mappings, owner/succession/last-owner transaction protection, permission change audit & member management, strict RLS enforcement on existing story/media/RPC policies, and RLS integration tests. These are CT-02c/CT-03 gates, not claimed complete here.
