# CT-08 operational runbook — STAGED, NOT ACTIVATION AUTHORIZATION

## Provider decision
Prefer Supabase Cron (pg_cron) running the private SQL executor directly in the same database, not a public HTTP endpoint, service-role key, Vercel Hobby cron or external secret. Official docs checked November 24, 2026: https://supabase.com/docs/guides/cron and https://supabase.com/docs/guides/database/functions. Proposed one-minute cadence, batch 5, provider-level statement timeout and maximum runtime to be measured. Actual account/extension, execution identity, timezone and cadence must be confirmed on a disposable hosted environment before any live job. Prior hosted read-only preflight found no pg_cron or reviewed queue. No cron install in migration.

## Approval gate and sequence
1. Verify backup/restore, ordered migrations, owner setup, RLS/advisors, actual hosted Auth and access checks, production feature flags and integration QA. Confirm scheduler stays paused after migration. Review every pending/legacy story, approval and media; do not auto-convert legacy scheduled status. Existing legacy schedule must be explicitly reconciled by editor/owner.
2. On approved disposable environment only, test using the actual database job execution identity (must be postgres with no auth JWT), including a future approved draft and revision, cancellation, revoked approval, contention and provider failure. Use test content, not production stories.
3. Obtain explicit production approval for provider installation and separate execution enablement. Create a uniquely named single job targeting `select newsroom_private.run_due_reviewed_publications(5)` as postgres, proposed every minute. Keep control paused until job identity, cadence, provider logs and absence of duplicate jobs verified. Never expose a public execution RPC. Configure provider monitoring for failed/missed jobs, and ensure timeout bounds; no actual monitoring/alert delivery is implied by this runbook.
4. Only after review, a trusted database operator can call `select newsroom_private.set_scheduler_enabled(true, 'Approved production activation reference ...')`. Confirm first completed run and actual publication of approved test content; check provider run details and internal ledger. Recent heartbeat means committed invocation only, not a guarantee of job installation or future execution.

## Monitoring and recovery
- Schedule, Dashboard and Contributor show minimal global health only to calendar-authorized staff. 5-minute stale threshold assumes proposed one-minute cadence; calibrate before activation. No queue totals, operator reason, raw failure codes or run IDs exposed to staff. A paused or busy invocation is not a heartbeat. Failed whole transactions cannot persist their own failure row; provider run details and external alerting remain authoritative for missed/failed jobs.
- Trusted database operator can read private scheduler_run_history (recent finished_at, published/blocked/retried), scheduler_control and scheduler_control_history; use bounded queries, no personal data or public grants. Confirm retention and controlled deletion policy before production use (no automatic pruning added). Review due pending rows and blocked rows through scoped calendar UI.
- For incident containment, pause via `select newsroom_private.set_scheduler_enabled(false, 'Incident reference and reason ...')`. Pause serializes with any running invocation; lock timeout is an explicit failure, retry after verifying no running transaction, then verify paused state. Do not assume an in-flight publication was undone. Separately disable the provider job and verify no duplicate jobs. Preserve all queue/run/audit history. Do not change a queue state or bypass approval manually.
- For a blocked story, inspect current authority/approval/media and correct the underlying issue. Cancel exact queue using authorized story action; obtain fresh review if source changed; schedule anew or use approved immediate publication only after cancel. Original due timestamp is retained on retry; backoff is minimum delay not a delivery SLA.
- Whole transaction failure: reconcile persisted state and event history, inspect provider error, only allow another invocation after confirming current control and permission. Existing idempotence/validation prevents duplicate publication. Pause during unresolved incidents.
- Rollback before release: revert application contract and restore prior executor from CT08c.1; do not drop control/run history after live use without preserving evidence. Never restore unpaused execution inadvertently.
